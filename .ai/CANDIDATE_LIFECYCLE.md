# QuantCairn Candidate Lifecycle Contract

> Purpose: freeze the meaning of `candidate_lifecycle_state` as a read-only, bundle-derived, candidate-level contract.
>
> Scope: documentation only. This file does not change selector logic, scoring, ranking, broker behavior, trading execution, or config writing.

## 1. Contract Summary

`candidate_lifecycle_state` is a **candidate-level field** that describes where a candidate sits in the lifecycle of the QuantCairn pipeline.

It is:

- **Generated by `SelectionBundle`**
- **Derived from existing authoritative fields**
- **Read-only**
- **Not a decision input**

It is **not** a new source of truth. It is a frozen view assembled from already-existing fields and artifacts.

## 2. Non-Goals

This contract must not:

- change selector behavior
- change scoring or ranking
- change data quality gates
- change broker / paper broker behavior
- change trading engine behavior
- change config writer behavior
- change scheduler behavior
- change notification delivery behavior

## 4. Enum

The canonical `candidate_lifecycle_state` enum is:

- `RESEARCH_ONLY`
- `VALIDATION_PENDING`
- `VALIDATED`
- `TRADE_READY`
- `PAPER_READY`
- `LIVE_READY`
- `FINAL_SELECTED`
- `UNKNOWN`

## 5. State Priority

When multiple signals are present, the lifecycle state must be derived using the following priority:

1. `FINAL_SELECTED`
2. `LIVE_READY`
3. `PAPER_READY`
4. `TRADE_READY`
5. `VALIDATED`
6. `VALIDATION_PENDING`
7. `RESEARCH_ONLY`
8. `UNKNOWN`

This priority is one-way for presentation. It does not change any upstream state.

## 6. State Definitions

### 6.1 `RESEARCH_ONLY`

The candidate is still in the research layer.

Typical indicators:

- `validation_status == AI_CANDIDATE`
- no trade admission
- no paper/live eligibility

Meaning:

- interesting for research
- not yet a tradable candidate

### 6.2 `VALIDATION_PENDING`

The candidate has entered the validation pipeline but has not yet completed it.

Typical indicators:

- `validation_status` is one of:
  - `CLASSIFIED`
  - `BENCHMARK_ASSIGNED`
  - `STRATEGY_ASSIGNED`
  - `PENDING_DATA_VALIDATION`
  - `DATA_VALID`
  - `PENDING_BACKTEST`
  - `BACKTEST_COMPLETE`
  - `PENDING_WALK_FORWARD`
  - `WALK_FORWARD_COMPLETE`
  - `PENDING_SHADOW`
  - `SHADOW_OBSERVING`

Meaning:

- still being validated
- not yet a finished candidate

### 6.3 `VALIDATED`

The candidate has completed the validation chain but has not yet been promoted to execution-ready status.

Typical indicators:

- `validation_status == SHADOW_COMPLETE`
- `paper_enabled == False`
- `live_enabled == False`
- `trade_admission_status != TRADABLE`

Meaning:

- validated
- not yet ready for execution

### 6.4 `TRADE_READY`

The candidate has passed the data-quality and formal-trade readiness gates, and is available as a formal trade candidate.

Typical indicators:

- `data_status == COMPLETE`
- `market_data_sufficiency == COMPLETE`
- `formal_scoring_eligibility == True`
- `score_type == FORMAL`
- `score_is_current_run == True`
- `trade_admission_status == TRADABLE`

Meaning:

- eligible for the formal trade pipeline
- not automatically paper/live eligible

### 6.5 `PAPER_READY`

The candidate is approved for paper trading.

Typical indicators:

- `validation_status == PAPER_ELIGIBLE`
- or `paper_enabled == True`

Meaning:

- paper execution may use this candidate
- not equivalent to live eligibility

### 6.6 `LIVE_READY`

The candidate is approved for live trading.

Typical indicators:

- `validation_status == LIVE_ELIGIBLE`
- or `live_enabled == True`
- and paper readiness has already been satisfied

Meaning:

- eligible for live execution
- does not imply this run selected the candidate

### 6.7 `FINAL_SELECTED`

The candidate is part of the final selected result set for the current committed selection run.

Typical indicators:

- symbol appears in `final_selected_symbols`
- or symbol appears in the committed selection bundle's formal selected set

Meaning:

- this run's final output
- not merely eligible

### 6.8 `UNKNOWN`

The system cannot safely determine the lifecycle state.

Typical indicators:

- missing required fields
- conflicting historical artifacts
- legacy bundle/report structure

Meaning:

- safe fallback
- not a trading signal

## 9. Backward Compatibility

This field is backward compatible by design.

Rules:

- Existing bundles without `candidate_lifecycle_state` remain readable.
- Existing reports remain valid.
- Existing consumers must continue to rely on the original fields when the new field is absent.
- The new field must never overwrite or reinterpret legacy values.
- Historical artifacts are not required to be rewritten.

Fallback behavior:

- If `candidate_lifecycle_state` is missing, consumers must fall back to the legacy fields.
- If the new field conflicts with legacy fields, the legacy fields remain authoritative for behavior and the conflict should be surfaced in diagnostics/tests.

## 10. Safety Boundary

`candidate_lifecycle_state` is a presentation and audit contract only.

It must never:

- bypass data quality gates
- bypass risk gates
- bypass broker safety
- bypass paper gate
- bypass live gate
- alter selector output
- alter final selected symbols
- alter TOP config publication

## 11. Minimal Implementation Boundary

If implemented in code later, the minimal safe scope should be:

1. `src/openalpha/selection_bundle.py`
   - build the derived field into the committed bundle/report payload

2. `src/dashboard/combined.py`
   - display the derived field only

3. `src/notifier/alerts.py`
   - display the derived field only

4. `tests/`
   - verify backward compatibility and non-interference

No execution-path module should depend on this field for control flow.
